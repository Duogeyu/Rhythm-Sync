## 2023-10-27 - [Optimize Levenshtein Distance Calculation]
**Learning:** In the Node.js backend, synchronous string matching algorithms like `levenshteinDistance` run single-threaded and block the event loop. The original implementation used a 2D matrix (`const matrix = []`), resulting in $O(N \times M)$ memory allocations and massive Garbage Collection (GC) overhead during bulk matching tasks.
**Action:** Always optimize dynamic programming matrix calculations in high-frequency Node.js loops by using an $O(N)$ 1D array approach combined with a globally shared `Uint16Array` buffer for standard lengths. Include a dynamic allocation fallback for inputs that exceed the buffer's maximum length.
## 2024-03-24 - [Extract string normalization and Levenshtein functions to module level]
**Learning:** In highly trafficked Node.js loops (like string similarity checks), defining helper functions and Regular Expressions inline inside route handlers or iteration loops causes V8 to continuously allocate new closures, compile regex objects, and trigger excessive Garbage Collection overhead. Furthermore, `String.prototype.replace()` in JavaScript can safely use global (`/g`) module-level Regular Expressions concurrently without state-leakage because `replace` execution does not rely on or mutate `lastIndex` like `exec` does.
**Action:** Always extract static regular expressions and utility functions (`normalizeTitle`, `normalizeArtist`, `levenshteinDistance`) to module-level scope or external utility files (`server/utils.js`) to ensure they are compiled and allocated only once. When moving `levenshteinDistance`, ensure its shared state buffers (`Uint16Array`) are moved alongside it.
